# tooltip

2026-09-16, transformation engine (positioner-model restructure per overlays.md + universal-patterns.md), verdict: clean, one behavior delta flagged (animation idiom), no other consumer breakage.

## Changed

- `src/components/ui/tooltip.tsx:1` — swapped the legacy individual-package import `import * as TooltipPrimitive from '@radix-ui/react-tooltip'` for the unified subpath import `import { Tooltip as TooltipPrimitive } from '@base-ui/react/tooltip'` (per universal-patterns.md's "individual packages" import rule). Dropped the now-unused `import type { ComponentProps } from 'react'`.
- `TooltipProvider` (line 4) — renamed `delayDuration` → `delay` (prop name, destructure default, and the value forwarded to `<TooltipPrimitive.Provider>`). Default kept at `0` (the project's own choice — Radix's own default was 700ms, Base UI's Trigger default is 600ms, but this wrapper has always forced instant-open tooltips project-wide via `delayDuration = 0`; preserved that intent instead of adopting either library's stock default). Type changed `ComponentProps<typeof TooltipPrimitive.Provider>` → `TooltipPrimitive.Provider.Props`.
- `Tooltip` (line 8) and `TooltipTrigger` (line 16) — type-only changes, `ComponentProps<typeof TooltipPrimitive.X>` → `TooltipPrimitive.X.Props`; no prop or structural changes needed on either part.
- `TooltipContent` (line 20) — restructured from Radix's `Portal > Content` into Base UI's `Portal > Positioner > Popup`, per the "biggest structural change" in universal-patterns.md:
  - Added `side`, `align`, `alignOffset` to the destructure alongside the existing `sideOffset` (kept its `= 0` default — the project's own choice, not Base UI's `4`/Radix's `0` stock defaults, since this file never hardcoded a different value before) and typed them via `Pick<TooltipPrimitive.Positioner.Props, 'align' | 'alignOffset' | 'side' | 'sideOffset'>` intersected with `TooltipPrimitive.Popup.Props`.
  - Per the "Positioner props: Pick means FORWARD" hard rule, all four are explicitly declared → destructured → forwarded onto the new `<TooltipPrimitive.Positioner>` (lines 32-37); leaving them in `...props` would have silently landed them on `Popup` (wrong DOM node) and broken `side="left"` at `card.tsx:150`, which is this component's only real-world positioning override.
  - `<TooltipPrimitive.Positioner className="isolate z-50">` — new wrapper element with no Radix precedent, given the conventional `isolate z-50` stacking-context classes from wrapper-shapes.md (Popup keeps its own pre-existing `z-50`).
  - `Content` → `Popup` rename; `data-slot="tooltip-content"` kept on `Popup` (the styled box), matching "keep data-slot on the parts the radix wrapper already had."
  - CSS var: `origin-(--radix-tooltip-content-transform-origin)` → `origin-(--transform-origin)` per the class-mapping.md CSS variable table.
  - Animation idiom rewrite (class-mapping.md "Animation idiom" section): the old `fade-in-0 zoom-in-95 animate-in` / `data-[state=closed]:fade-out-0 data-[state=closed]:zoom-out-95 data-[state=closed]:animate-out` pair relied on Radix's enumerated `data-state="delayed-open"|"instant-open"|"closed"` attribute, which Base UI's Popup does not emit (Base UI only exposes the presence attributes `data-open`/`data-closed`/`data-starting-style`/`data-ending-style`). Restated as a CSS-transition idiom instead of a 1:1 selector rename: `transition-[transform,opacity] data-starting-style:opacity-0 data-starting-style:scale-95 data-ending-style:opacity-0 data-ending-style:scale-95`, plus the original per-side slide-in kept as parameterized `data-[side=…]:data-starting-style:*translate-{x,y}-2` rules (slide-in-on-enter only, matching the original file's own asymmetric design — it never had a slide-out either).
  - `TooltipPrimitive.Arrow` — left the className byte-for-byte identical (see "Left alone"); only its parent changed from `Content` to `Popup`.
  Leftover scan: `grep -n "radix-ui\|@radix-ui" tooltip.tsx` → no matches.
- `src/components/ui/card.tsx` — no code change. Verified `TooltipTrigger` (line 150, `<TooltipTrigger type="button" className="cursor-help transition-colors hover:text-foreground">`) still type-checks and behaves correctly: Base UI's `TooltipTrigger` renders a real `<button>` by default (`BaseUIComponentProps<'button', State>` in `node_modules/@base-ui/react/tooltip/trigger/TooltipTrigger.d.ts`), so a plain native `type="button"` attribute passes straight through exactly as it did with Radix — no `render`/`nativeButton` needed since we never swap the rendered element away from `<button>` here. `side="left"` (line 153) is now handled by the Positioner forwarding described above.

## Left alone

- `TooltipPrimitive.Arrow` className (`z-50 size-2.5 translate-y-[calc(-50%_-_2px)] rotate-45 rounded-[2px] bg-primary fill-primary`) kept verbatim. This is the classic shadcn "rotated square" diamond trick — it paints the Arrow element's own CSS box (not an inner SVG shape) as a solid rotated square, which works identically whether Arrow renders an `<svg>` (Radix) or a `<div>` (Base UI, confirmed in `TooltipArrow.d.ts`). The single fixed `translate-y` nudge only pulls the diamond into a seamless overlap on the vertical (top/bottom) axis; it was never side-aware even before this migration (no `data-[side=…]` classes existed on the Arrow in the original file), so `side="left"` in `card.tsx` gets the same not-fully-centered arrow it always got. Not fixing this — it's a pre-existing cosmetic characteristic, not something the migration introduced, and adding new per-side arrow offsets would be a redesign beyond a mechanical port.
- No global `TooltipProvider` exists anywhere in `apps/web/src` outside `tooltip.tsx` itself — grepped `TooltipProvider` and `from '@/components/ui/tooltip` across `apps/web/src`, `src/routes/__root.tsx`, and `src/main.tsx`; the only usages are `tooltip.tsx`'s own internal wrapping and `card.tsx`'s `Tooltip`/`TooltipContent`/`TooltipTrigger` import. There is no app-wide provider call site needing a `delayDuration`→`delay` rename beyond the one inside `tooltip.tsx` itself (already handled above).
- `src/index.css`'s comment block (lines 7-9) still lists "tooltip" among the components relying on `tw-animate-css`'s `animate-in`/`fade-in`/`zoom-in`/`slide-in-from` classes. That's now slightly stale — tooltip no longer uses those utilities — but `dialog`, `select`, and `dropdown-menu` still do (not yet migrated), and touching shared CSS comments was outside this task's declared file scope, so left as-is.

## Behavior changes

- FLAG: enter/exit animation mechanism changed from Tailwind keyframe utilities (`animate-in`/`animate-out`/`fade-in-0`/`zoom-in-95`) gated on Radix's `data-state` enum, to Base UI's transition-based `data-starting-style`/`data-ending-style` idiom. Visually this should look equivalent (same fade + scale-95 + directional slide-in-on-open), but the underlying CSS mechanism is a `transition` on `transform,opacity` rather than a `@keyframes` run, so exact easing/duration curves are governed by whatever `transition` defaults apply (no explicit duration/timing-function class was added, matching the original file's lack of one — it also never set an explicit animation-duration class itself, relying on tw-animate-css defaults).
- FLAG (no code impact today): `disableHoverableContent` (Radix) → `disableHoverablePopup` (Base UI, renamed, lives on `Tooltip.Root`) has no automatic carry-over — this project's wrapper never exposed or set it, and no call site uses it, so nothing to change, but any future consumer expecting the old Radix prop name will get a plain unknown-prop TS error instead of a silent behavior change.
- Not a behavior change, but note: `TooltipProvider`'s `delay` (ex-`delayDuration`) still defaults to `0` here, same as before — tooltips project-wide continue to open instantly with no hover delay.
